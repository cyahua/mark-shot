# GUI 内存测量

## 测量口径

2026-10-15，Linux x86_64、Qt 6.12.0、16 个逻辑处理器、Release。
使用真实窗口类、Fusion 样式和 offscreen 平台，默认输入为 3840 x 2160 的固定 RGB32 图案，DPR 为 1。
不捕获用户桌面，不读取用户配置，不启动生产入口中的空闲回收器。
两版均使用生产程序原有的 glibc 1 MiB 图像分配阈值，不调用工作集回收或主动整理堆。

对照版恢复 GUI 优化前的实现，保留此前已有的录制、打包、区域分析和插件优化，
也保留集成、插件两个设置页原有的延迟创建。两版共用修正后的测量入口与其余应用对象。
每个场景启动独立进程，前后版本交替运行三次，表格取中位数。

对照程序必须与新版位于同一运行目录，使用相同插件、配置、样式与应用名称。
工具记录每个阶段的实际可见窗口像素数，本次全部前后记录均逐项相同。
早期调用 `QThreadPool::waitForDone()` 或把对照程序放在其他插件目录的测量不纳入结果。
Qt 文档明确说明该方法会移除线程池中的线程，正常阶段等待现改为检查任务是否完成，保留工作线程。

参考：[QThreadPool::waitForDone](https://doc.qt.io/qt-6/qthreadpool.html#waitForDone)。

## 结果

单位为 MiB，峰值取进程 RSS 与系统维护的峰值记录；关闭后等待窗口销毁，但不强制回收内存。
耗时包含脚本中的固定等待，不等同于纯渲染耗时。

| 场景 | 原峰值 | 新峰值 | 原关闭后 RSS | 新关闭后 RSS | 原耗时 / 新耗时（ms） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 4K 截图选区 | 151.7 | 151.8 | 80.7 | 81.0 | 331 / 352 |
| 4K 标注、撤销、重做 | 151.9 | 137.0 | 81.3 | 73.8 | 745 / 688 |
| 4K 图片编辑、缩放 | 193.9 | 173.7 | 81.2 | 73.8 | 605 / 531 |
| 4K 单独贴图 | 111.0 | 110.9 | 47.9 | 47.8 | 313 / 314 |
| 4K 贴图与编辑同时打开 | 215.8 | 168.7 | 81.4 | 73.8 | 676 / 604 |
| 设置，访问全部页面 | 102.1 | 102.1 | 100.3 | 100.2 | 1286 / 1307 |
| 4K 混合操作，三轮 | 280.6 | 215.5 | 145.1 | 115.8 | 11564 / 10816 |
| 4K 编辑，连续六档缩放 | 223.6 | 173.8 | 81.3 | 73.9 | 1269 / 1195 |
| 1080p 混合操作，三轮 | 192.1 | 144.4 | 151.9 | 119.2 | 11015 / 10097 |

混合操作依次执行截图、标注、图片编辑、贴图、贴图编辑和设置。
标注包含 20 条笔画、10 次撤销及 10 次重做；设置逐一访问全部 11 页。
普通截图和单独贴图的峰值基本不变，不能把其他场景的收益套用到它们。
普通截图脚本耗时增加约 21 ms，访问全部设置页也略慢，不宣称所有操作都加速。

设置首次打开只创建常规页，控件数从 659 降至 149，RSS 从 74.5 降至 68.9 MiB。
访问全部页面后仍保留已创建页面与未保存输入，因此全部访问后的峰值没有下降。

连续 12 轮混合操作的峰值为 216.4 MiB。每轮窗口关闭后的 RSS 从首轮 115.7 增至末轮 116.7 MiB，
没有出现逐轮积累一幅 4K 图像的增长。工具本身会保存采样 JSON，这约 1 MiB 差额不能直接认定为应用泄漏。

**4K 混合场景仍超过 200 MiB，当前没有实现所有场景都低于 200 MiB。**
一幅 4K 32 位图像本身约占 31.6 MiB，还需计入窗口绘制缓冲、视口缓存、字体、插件和分配器空闲页。
关闭后 RSS 不为零，也不等于窗口或完整图像仍然存活。

## 实现

- `shot_window_setup.cpp` 直接保留 RGB32，不为没有透明度的共享原图执行无效预乘；需要转换的格式仍由 Qt 保护共享输入并优先就地转换。
- `shot_window_viewport_rendering.cpp` 按 32 个输出行处理，只保留各工作区需要的输入行；调用线程统一分配临时缓冲，不再保留整幅横向中间图像。
- `shot_window_canvas.cpp` 在生成新视口之前释放失效缓存，失败时仍绘制原图，不同时保留两幅全尺寸视口。
- 区域识别只在选区需要时启动，编辑、全图标注不预先执行分析；返回选区时仍生成完整候选。
- `region_detection_scheduler.cpp` 使用最多三个工作线程，避免临时图像分散到通用线程池的不同堆中；空闲回收检查该队列，应用退出前等待任务结束。
- `settings_dialog_pages.cpp` 管理全部页面的按需创建、保存基线及配置合并；未访问页面的配置保留，创建新页不吸收其他页面的草稿。

单线程识别队列曾使三个同时提交的 4K 请求从约 96 ms 增至 258 ms，已撤回。
最多三个线程的复测为原通用线程池 94 ms、专用队列 92 ms，不以明显降低常见多屏并发来换取内存读数。

## 回归与复现

Release 的 30 项相关回归、Debug 的 13 项 GUI 回归，以及精简 FFmpeg 构建的 8 项录制回归均通过。
200 MiB 连续缩放门槛实测：对照版退出码 1，新版退出码 0，两版均完成相同窗口尺寸下的六档缩放。

像素回归使用修改前的算法作为固定参考，覆盖五种像素格式、六种裁剪或缩放组合，逐像素比较输出。
共享透明输入、DPI、色彩空间和文本元数据均有回归；缓存测试检查旧缓冲确实在下一幅视口生成前释放。
窗口回归检查截图帧最终释放、编辑返回选区、贴图编辑、设置草稿与撤销、未访问页面配置、紧凑布局及高 DPI 重绘。
识别队列覆盖多个排队请求、原图生命周期和应用退出收尾。

```sh
cmake --build build-release --target \
  mark-shot-gui-memory-benchmark \
  mark-shot-canvas-image-memory-test \
  mark-shot-sharp-viewport-rendering-test \
  mark-shot-region-detection-scheduler-test --parallel 6

# 本机已验证：优化前超过门槛，优化后通过；仍完成六档实际缩放
QT_QPA_PLATFORM=offscreen QT_SCALE_FACTOR=1 \
  ./build-release/mark-shot-gui-memory-benchmark \
  --scenario edit --zoom-passes 6 --max-peak-mib 200

# 重复完整流程，不清空线程池，也不触发空闲回收
QT_QPA_PLATFORM=offscreen QT_SCALE_FACTOR=1 \
  ./build-release/mark-shot-gui-memory-benchmark --scenario cycle --iterations 12
```

本地原始数据位于 `build-release/gui-memory/final/`，汇总为 `comparison.json`。
对照源码及摘要保存在 `build-release/gui-memory/corrected-baseline/`；实际运行的对照程序为
`build-release/mark-shot-gui-memory-baseline`，与新版共享运行目录。

## 范围

这些数值只覆盖固定图案和软件窗口绘制，不包含真实桌面捕获、图片文件解码或 GPU 内存。
正确性回归覆盖透明图像，但表格中的内存输入是不透明 RGB32，不能直接推广到任意尺寸或像素格式。
Windows 原生窗口、工作集、私有提交量和完整安装包没有在本机实测。
此轮保留此前的录制与发行体积优化，分别见[录制内存](recording-memory.md)和[内存与发行体积](performance.md)。
